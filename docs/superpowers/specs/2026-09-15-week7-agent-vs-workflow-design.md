# Week 7 Task Set E — Agent Loop vs. Fixed Workflow

Status: approved by user (2026-09-15), pending spec self-review

## 1. Goal

Build a docs-migration Q&A system two ways — a tool-calling ReAct agent and a
hard-coded 3-step pipeline — over the same tools, same model, same 10
questions, and same output contract. Measure pass rate, p50 latency, total
tokens, and cost/question for both, enforce four hard budgets on the agent
loop, and write a verdict on whether the agent's flexibility was ever actually
needed.

No prior Week 7 code exists in this repo (git history stops at week6), so this
spec also covers the base 2-tool agent that Task Set E's prerequisite assumes
already exists.

## 2. Data source

`data/documents/input_files/developer_documentations/`:

- `github_combined_reference.pdf` (13 pages) — 5 real GitHub REST endpoints
  (render markdown, create issue, create PR, create repo, create release),
  each documented twice: once for API version `2022-11-28`, once for
  `2025-06-01`, with explicit deprecation call-outs between the two
  (e.g. `assignee` → `assignees`). This is the migration/deprecation source.
- `swagger_v2_reference.pdf`, `swagger_v3_reference.pdf` — docs about the
  Swagger Codegen CLI tool (not an API spec). Real searchable content, wrong
  topic for openapi/deprecation lookups — they exist to make `search_docs`
  return genuinely mixed results, the same way a real docs corpus would.

`data/documents/input_files/golden_sets/{gs_easy,gs_medium,gs_hard}.json` (45
Q&A pairs total) supplies the raw material for the 10 race questions —
especially `gs_hard`, whose entries already span both API versions of the
same endpoint, which is exactly the "step 3 depends on what step 2 found"
shape the task requires.

## 3. New structured data files (no fabrication)

Modeled on the existing `eval/spec/relay_openapi.json` /
`eval/spec/deprecations.json` pattern — every fact tagged with the PDF page
it came from, hand-extracted by reading the actual pages (already done during
brainstorming), not invented.

- `agent/spec/github_openapi.json` — per endpoint, per `api_version`: method,
  path, required/optional body params with defaults, `x-source: "page N"`.
- `agent/spec/deprecations.json` — one entry per deprecated
  field/param/behavior: which endpoint, which version it's deprecated *in*,
  the replacement, `x-source`.

Both tools below only ever return data already present in these two files —
nothing is generated by the LLM as "spec content."

## 4. Tools

All three share one JSON-schema tool-calling shape (Groq's client is
OpenAI-SDK-compatible: `tools=[{...}]`, function-calling `tool_choice="auto"`).

1. **`search_docs(query: str, k: int = 4)`** — hybrid dense+BM25 retrieval
   over all 3 PDFs, reusing `rag.pipeline.RAGPipeline.retrieve()` with a
   dedicated Chroma collection (`week7_docs`) so this doesn't touch the
   existing Relay-corpus collections from weeks 3–6. Description: "Search the
   indexed developer documentation for text relevant to a natural-language
   question. Use this first, for anything not about a specific endpoint's
   exact parameters or deprecation status."

2. **`get_openapi_spec(endpoint: str, api_version: Literal["2022-11-28", "2025-06-01"])`**
   — exact lookup into `github_openapi.json`. Description: "Return the exact
   method, path, and parameter list for one named GitHub endpoint at one
   specific API version. Use this only when you already know the endpoint
   name and need its precise parameter shape — not for open-ended search."

3. **`check_deprecation(endpoint: str, api_version: Literal["2022-11-28", "2025-06-01"])`**
   — exact lookup into `deprecations.json`. Description: "Report whether a
   named endpoint has anything deprecated as of one specific API version, and
   what replaces it. Use this only to check deprecation status — not to fetch
   the full parameter list (use get_openapi_spec) or to search prose (use
   search_docs)." This is the task's required 3rd tool: one job, enum
   `api_version`, no overlap with the other two.

Deliverable: a before/after diff of the tool `description` fields (2-tool →
3-tool) saved to `results/week7/tool_diff.md`.

## 5. Agent loop (`agent/loop.py`)

Standard ReAct loop against Groq chat completions with `tools=`:
1. Send system prompt + full running message history + tool schemas.
2. If the model returns `tool_calls`, execute each locally, append results as
   `role: tool` messages, loop.
3. If the model returns a plain answer, stop and return it.
4. Every lap's `usage.prompt_tokens + completion_tokens` is added to a running
   total — the common mistake called out in the task doc (counting only the
   final call undercounts by multiples) is avoided by design.

### Budgets (`agent/budgets.py`)

A `Budget` dataclass (`max_iterations`, `max_tokens`, `max_cost_usd`,
`max_wall_seconds`) checked at the *top of every loop iteration*, before the
next model call is made:
- iteration count > max_iterations
- running token total > max_tokens
- running cost (tokens × a per-model $/token table) > max_cost_usd
- `time.monotonic() - start > max_wall_seconds`

Any breach raises `BudgetExceeded(reason, partial_answer=None)` and the loop
returns a structured "terminated: budget" result instead of the model's
answer — clean stop, not a crash, not another silent lap.

Deliverable: one deliberately tight-budget run (e.g. `max_iterations=1` on a
question that needs 3 tool calls) with its full log saved to
`results/week7/budget_termination.log`, showing which budget fired.

## 6. Fixed workflow (`agent/workflow.py`)

Same tools, same model, same output contract, no decision loop:
1. Call `search_docs(question)` — always.
2. Extract endpoint name from the question deterministically (regex/keyword
   match against the 5 known endpoint names — the workflow is allowed to be
   dumb here, that's the point).
3. Call `get_openapi_spec(endpoint, api_version)`.
4. Call `check_deprecation(endpoint, api_version)`.
5. One final generation call with all 3 tool results as context, same system
   prompt as the agent's answer step.

If step 2 can't identify an endpoint, the workflow still runs steps 3–5 with
whatever it has (matching "no loop hiding inside it" — no retry, no
re-planning).

## 7. Race harness (`eval/week7/`)

- `questions.json` — 10 questions built from `golden_sets` content: a mix of
  single-endpoint lookups and ≥3 that require chaining
  (deprecated-in-`2025-06-01` → what replaced it), each with an expected
  answer fragment for pass/fail grading (reusing the existing
  `verify_citations`-style substring check pattern from `rag/generator.py`
  rather than inventing a new grading scheme).
- `run_race.py` — runs all 10 questions through both systems, records per-run
  latency, token totals, and estimated cost, computes pass rate / p50 latency
  / total tokens / cost-per-question for each system, writes
  `results/week7/race.csv` (8 numbers, 4 per system).

## 8. Verdict

`results/week7/verdict.md` — under 150 words, applies the decision rule ("does
the path vary by input?") to the actual race numbers and names the specific
question class (if any) that forces the agent, per the rubric's explicit
warning that a verdict contradicting the table scores 0.
